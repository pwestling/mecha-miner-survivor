# events-simultaneous-ordering
#
# Rule under test: doc 10 § System phase ordering - "Simultaneous outcomes use
# documented stable ordering rather than collection or thread timing." For an
# event batch the keys are: tick, then emitting system phase, then explicit
# emission sequence. There is no fourth key.
#
# There is no fourth key because the emission sequence is per-tick global:
# CMP-SIM-003 issues it monotonically across the whole tick regardless of phase
# or emitter, so (tick, sequence) is already a total order. A duplicate sequence
# within a tick is therefore an impossible input - a defect in the issuer, not a
# tie - and a comparator that fell through to a further key on a duplicate would
# silently order it and hide the bug that produced it. The former fourth key, the
# full emitting entity ID, has been replaced by a live invariant: sequence is
# unique within a tick, and a duplicate fails loudly. See
# EventOrdering.AssertSequenceUniqueWithinTick.
#
# This scoping is events only. Doc 20 § Boundary and tie ordering defines a
# separate five-key sort for damage instances - system phase, explicit attack
# sequence, target ID, source ID, then insertion sequence - and that is untouched
# by the rule above.
#
# Fixture: run session 0xE7E00001, tick 7, eight domain events emitted by four
# system phases (3, 8, 10, 11) with explicit emission sequences that deliberately
# disagree with phase order, so sorting cannot be a no-op. The same eight events
# are appended in two different orders - ascending and reversed - and both batches
# must equal the text below.
#
# The stored phase numerals are correct by contract, not by coincidence: doc 10 §
# System phase ordering numbers a fixed fourteen phases and those numerals are
# stable normative identifiers. Renumbering is forbidden; a new phase takes the
# next unused number and a subdivision keeps its parent's. So a fixture may store
# 3, 8, 10, 11 and rely on their meaning.
#
# Every identity here - four emitters and the shared subject - is drawn from the
# OrdinaryEnemy partition, which begins immediately after Player. Player's
# capacity is the doc 20 § Scope and invariants invariant "exactly one player
# entity exists until terminal resolution", so the OrdinaryEnemy offset is 1 by
# simulation invariant and no doc 22 § Performance and capacity combat ceiling
# precedes it. The fixture asserts that computed containment rather than assuming
# it. The previous fixture drew its subject from Pickup, which sits after all
# three doc 22 ceilings, which is why the literal 3830 was baked in here and
# would have made this ordering golden fail when the enemy-projectile ceiling
# moved.
#
# Derived by: the documented rule read off doc 10 and doc 20, computed in an
# independent Python reference before any C# ran, and cross-checked against an
# independent list sort in EventOrderingTests. Not by accepting whatever the
# buffer emitted.
